# Lily Module Protocol v1

This document and [`module-manifest.v1.schema.json`](./module-manifest.v1.schema.json)
define the public module-manifest contract consumed by Hugo themes and LilyMap.
The protocol identifier is `lily-module/v1` (also written
`lily-module-protocol/v1` in runtime metadata).

## Compatibility rules

- A missing `apiVersion` is a legacy v1 manifest and is interpreted as
  `lily-module/v1`. New modules should declare it explicitly.
- v1 implementations preserve unknown manifest fields and unknown saved
  configuration values. They must not rewrite or discard fields they do not
  understand.
- Adding optional fields, schema types, or capabilities with safe defaults is a
  compatible v1 change. Changing existing field meaning, removing a field,
  changing placement semantics, or making previously valid content invalid is
  breaking and requires `lily-module/v2` plus a migration path.
- `version` is the individual module's SemVer. It is independent of the protocol
  identifier; a module may release a new major version while remaining on v1
  only when its manifest remains valid for v1 consumers.
- Runtime implementation metadata (`data/lily/runtime.yaml` `version`) is not a
  substitute for the protocol identifier. Consumers must gate compatibility on
  `protocol` / `apiVersion`.

## Manifest contract

A manifest is one YAML mapping, normally stored as
`data/lily/modules/<id>.yaml`. `id` matches the filename and is lowercase
hyphenated. `allowedSlots` declares every legal `layout.slot` placement.
`template.partial` resolves below the theme/site partial root. Declared `assets`
resolve below the asset root. `defaults` provides initial configuration and
`schema` describes editable fields and their UI metadata. A layout instance
contains a unique `id`, a manifest `module` id, and optional `enabled`, `order`,
and `config` values.

The schema describes structure and field definitions; consumers must also
validate configured values against the declared field type, bounds, and options.
For `select` fields, `options[].value` is intentionally JSON-compatible rather
than string-only; editors must preserve the selected value's original type
instead of coercing it through the HTML `<select>` string value. Compatibility
fixtures live in [`v1-fixtures.json`](./v1-fixtures.json) and are consumed by
LilyMap integration tests. Module templates and browser assets are trusted code,
not sandboxed extensions.

## Release policy

Keep the v1 schema and compatibility fixtures in source control. Every protocol
change must update this document, the machine-readable schema, and compatibility
checks in LilyMap and the site integration workflow. Do not silently reinterpret
old v1 data. Introduce a new protocol identifier for a breaking change.
